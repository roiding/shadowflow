# 东方财富 push2/push2his 行情接口调用规范

> 版本：1.5（2026-08-17）
> 依据：真实 Chromium 请求时间线、curl 复刻以及 Go 客户端重复测试
> 适用范围：`push2.eastmoney.com`、`push2delay.eastmoney.com`、`push2his.eastmoney.com` 下的 `/api/qt/*` 行情接口

本文记录 ShadowFlow 使用东方财富行情接口时的请求规范和故障处理基线。暗盘榜单、字段口径和板块关系的完整资料仍见 [项目记忆](../项目记忆.md)。

## 1. 已验证结论

当浏览器能显示行情，而 curl、Go 或 Node 请求出现 `Empty reply from server`、`EOF`、`UND_ERR_SOCKET` 或 `net::ERR_EMPTY_RESPONSE` 时，请求已发出但服务端在返回 HTTP 响应前断开了连接。

2026-08-16 的请求时间线曾观察到：

1. 页面初次发出的无 Cookie 行情请求被断开；页面 JavaScript 生成访客 Cookie 后，重试请求返回 200。
2. 相关 Cookie 未通过服务器 `Set-Cookie` 下发，而是在浏览器本地生成，值由随机数和时间戳构成。
3. 这只能证明当次重试时间线与 Cookie 出现时间相关，不能证明 Cookie 是所有成功请求的必要条件。

2026-08-17 使用“每次请求生成新 Cookie”的 curl 客户端复测：

1. `push2his` 确实支持 `secid=90.BKxxxx` 的概念和行业板块历史日 K，并非只支持个股。
2. 完整访客 Cookie、Chrome 请求特征、对应详情页 `Referer` 和网页 JSONP 参数可以取得合法响应，但只能证明请求具备成功条件，不能据此认定批量调用已经稳定。
3. 全局约 `0.77 QPS` 时，概念和行业样本各自首次成功，随后 8 个请求全部在收到 HTTP 响应前被断开。固定复用一套按格式生成但从未成功过的 Cookie，按 0、10、10、20、40 秒阶梯请求也全部失败。
4. 这组结果只描述该 curl 会话模型，不能推出东方财富存在通用的 `1 QPS`、10 秒、20 秒或其他固定冷却时间。

同日使用真实东方财富页面和同一内置浏览器会话复测：

1. `BK1650` 概念日 K 和 `BK0448` 行业日 K 均成功绘制；同一浏览器会话切换板块后仍可取得有效日 K。
2. `BK0448` 页面初次加载时，在 142 毫秒内观察到 30 个 `stock/kline/get` 资源请求：日 K 13 个、周 K 7 个、月 K 10 个。
3. 请求同时包含完整历史、`lmt=120`、`lmt=1` 等不同版本。页面会预取多个周期和粒度，周期按钮随后可能只切换已预取数据。
4. 真实页面能在毫秒级突发请求后绘制 K 线，因此“接口要求每次请求冷却 10 或 20 秒”的假设不成立。curl 的连续空响应应优先归因于会话建立、Cookie 生成方式、请求指纹或客户端行为差异，而不是仅凭请求频率解释。

同日进一步完成 Cookie 必要性与复用验证：

1. 一个纯 HTTP 生成 Cookie 会话首次成功后，保持整套 Cookie 不变，在约 3 秒内连续请求 5 个概念/行业板块全部成功，证明同一 Cookie 可以复用。
2. 同一冻结 Cookie 在 10 秒后的请求返回空响应；保持身份字段不变并刷新 `st_psi`，10 秒和 20 秒请求仍失败。因此没有证据支持“Cookie 固定有效 10 秒”或“刷新 `st_psi` 即可续期”。
3. curl 不带 Cookie 也取得过 HTTP 200、`rc=0` 和完整 `BK1650` 日 K。
4. 已保存的两条浏览器成功 HAR 请求均没有请求 Cookie，响应也没有 `Set-Cookie`。Cookie 既不是已证实的必要条件，也不是稳定成功的充分条件。
5. curl 全部空响应的同一时间窗口，真实浏览器仍成功重新加载 `BK1650` 日 K 并生成完整图表。固定到此前成功过的边缘 IP 也不能恢复 curl，说明 Cookie、等待时间、出口 IP 和单一边缘节点都不足以独立解释失败。
6. 当前最符合证据的判断是服务端会综合客户端连接特征、请求行为和临时状态进行分类；具体决定因素仍未完成最小化验证。

同日固定出口、固定边缘 IP 的快速状态窗口实验进一步确认：

1. 出口 IPv4 哈希在实验前后保持一致；所有 curl 请求显式绕过系统代理、固定 IPv4、HTTP/1.1 和东财边缘 IP。
2. 在边缘 `101.42.128.173` 上，无 Cookie 请求 `BK1650` 失败后，新 Cookie 请求成功；500 毫秒后去掉 Cookie 再请求同一个 `BK1650` 成功，但再切换到 `BK0448` 失败。
3. 因此存在“成功 Cookie 后同标的无 Cookie 短时继承”的现象，但没有证据支持整个出口 IP 对所有板块统一开窗。
4. 独立静默 60 秒建立成功 Cookie 后，同一冻结 Cookie 的 1 秒、2 秒和 5 秒间隔请求成功，8 秒间隔首次失败。该 curl 客户端的活跃复用边界位于 5 至 8 秒之间。
5. 旧 Cookie 失败后，新 Cookie 在累计 0、2、5、10、20 秒均失败，40 秒恢复成功；因此连续探针条件下的可操作恢复区间为 20 至 40 秒，保守退避值为 40 秒。
6. 恢复成功的新 Cookie 完全静默 10 秒后再次失败；同一时间窗口真实浏览器仍成功加载 `BK1650` 日 K。上述窗口属于当前 curl 客户端状态，不是浏览器或接口的全局 CD。

这些结论是特定日期的黑盒实测，不是东方财富公开合约。服务端策略可能变化，排障时必须重新做最小化复现和重复验证。

## 2. Cookie 观察记录

以下 Cookie 曾在真实页面中观察到，作用域为 `.eastmoney.com`，使用 `; ` 拼接到单个 `Cookie` 请求头。它们是请求复刻的候选变量，不是已证明必须携带的接口凭证：

| Cookie | 格式 | 说明 |
|---|---|---|
| `qgqp_b_id` | 32 位小写十六进制 | 随机设备标识 |
| `st_pvi` | 14 位数字 | 随机浏览标识 |
| `st_si` | 14 位数字 | 随机会话标识 |
| `st_sp` | URL 编码的本地时间 `YYYY-MM-DD HH:MM:SS` | 首次进入时间 |
| `st_inirUrl` | 空字符串 | 写作 `st_inirUrl=` |
| `st_sn` | 数字 | 当前可固定为 `1` |
| `st_psi` | `YYYYMMDDHHMMSScc-12位数字-10位数字` | 时间戳与随机数组合 |
| `st_asi` | `delete` | 当前观察到的固定值 |
| `st_nvi` | 约 22 位字母数字串 | 随机访客标识 |
| `nid18` | 32 位小写十六进制 | 随机设备标识 |
| `nid18_create_time` | epoch 毫秒 | 与 `nid18` 配对 |
| `gviem` | 25 位字母数字串 | 随机访客标识 |
| `gviem_create_time` | epoch 毫秒 | 与 `gviem` 配对 |

如果客户端选择携带这些 Cookie，应在同一逻辑会话内保持身份字段稳定。不要为每个请求都生成全新身份；但也不能把“同一 Cookie 复用”当作稳定成功保证。冻结 Cookie、刷新 `st_psi` 和完全不带 Cookie 都分别出现过成功与失败。

示例仅用于说明格式，不应作为固定常量长期复用：

```text
qgqp_b_id=9c093b604ee28a538b4990354e15ea30; st_pvi=97983609924472; st_si=39033622944812; st_sp=2026-08-16%2021%3A41%3A09; st_inirUrl=; st_sn=1; st_psi=2026081621410970-113200301353-8840031495; st_asi=delete; st_nvi=RkSapperdWX4Yer871MKd6; nid18=0e47c46aa4a10727883d87f82d087003; nid18_create_time=1786887670194; gviem=bgwmXsXh4UDcTlqwV2O4Qb6f9; gviem_create_time=1786887670195
```

## 3. 通用请求特征

推荐从真实 Chrome 请求复刻以下请求头，并让 `Referer` 与标的类型对应：

```text
sec-ch-ua: "Not=A?Brand";v="99", "Google Chrome";v="<version>", "Chromium";v="<version>"
sec-ch-ua-mobile: ?0
sec-ch-ua-platform: "macOS"
user-agent: <与 sec-ch-ua 一致的 Chrome User-Agent>
accept: */*
sec-fetch-site: same-site
sec-fetch-mode: no-cors
sec-fetch-dest: script
referer: https://quote.eastmoney.com/<对应页面>
accept-encoding: gzip, deflate, br, zstd
accept-language: zh-CN,zh;q=0.9,en;q=0.8
cookie: <可选；若使用则保持逻辑会话一致>
```

请求头顺序在本次实验中没有被证明是单独的必要条件，但实现应尽量保持浏览器顺序。不要先引入 TLS 指纹依赖；先用标准库完成“完整复刻 -> 重复成功 -> 逐项删减”。

`ut=fa5fd1943c7b386f172d6893dbfba10b` 是当前网页使用的公共 token，不是用户登录凭证。它仍属于非公开参数，必须允许配置或在回归测试失败时重新从页面请求确认。

## 4. 历史 K 线

```text
GET https://push2his.eastmoney.com/api/qt/stock/kline/get
```

主要参数：

| 参数 | 说明 |
|---|---|
| `secid` | `1.600519` 为沪市，`0.000001` 为深市，`90.BK1650` 为板块 |
| `ut` | 当前网页公共 token |
| `fields1` | `f1,f2,f3,f4,f5,f6` |
| `fields2` | `f51,f52,f53,f54,f55,f56,f57,f58,f59,f60,f61` |
| `klt` | `5` 五分钟，`101` 日 K，`102` 周 K，`103` 月 K |
| `fqt` | `0` 不复权，`1` 前复权，`2` 后复权 |
| `beg` / `end` | 日期范围；项目五分钟归档使用同一交易日的 `YYYYMMDD` |
| `smplmt` | 日 K 实测单次最多返回 460 根，完整历史必须分段 |
| `cb` | JSONP 回调名；按网页调用时建议保留 |
| `_` | epoch 毫秒缓存破坏参数；按网页调用时建议保留 |

日 K 浏览器请求模板：

```text
https://push2his.eastmoney.com/api/qt/stock/kline/get?cb=jQuery3510<19位随机数字>_<epoch_ms>&secid=90.BK1650&ut=fa5fd1943c7b386f172d6893dbfba10b&fields1=f1%2Cf2%2Cf3%2Cf4%2Cf5%2Cf6&fields2=f51%2Cf52%2Cf53%2Cf54%2Cf55%2Cf56%2Cf57%2Cf58%2Cf59%2Cf60%2Cf61&klt=101&fqt=1&beg=0&end=20500101&smplmt=460&lmt=1000000&_=<epoch_ms>
```

个股五分钟归档请求不需要照搬日 K 的日期范围，使用：

```text
secid=<market.code>&klt=5&fqt=0&beg=<YYYYMMDD>&end=<YYYYMMDD>
```

带 `cb` 时响应为 JSONP，解析时取第一个 `(` 与最后一个 `)` 之间的 JSON。无 `cb` 时当前接口可返回 JSON，但反爬策略变化后应优先按真实网页参数复刻。

JSONP 去壳后的主要响应结构：

```json
{
  "rc": 0,
  "data": {
    "code": "BK1650",
    "market": 90,
    "name": "通信技术",
    "decimal": 2,
    "dktotal": 105,
    "preKPrice": 1000.0,
    "klines": [
      "2026-03-16,998.66,1006.75,1006.75,984.58,113005733,378869460159.00,2.22,0.68,6.75,2.92"
    ]
  }
}
```

应先校验 `rc == 0`、`data != null` 和 `klines` 数量，再解析行字段。`dktotal` 是服务端报告的总 K 线数，不代表本次响应已经返回全部历史。

`klines[]` 与 `fields2` 的对应关系：

| 字段 | 含义 |
|---|---|
| `f51` | 日期或分钟时间 |
| `f52` / `f53` | 开盘 / 收盘 |
| `f54` / `f55` | 最高 / 最低 |
| `f56` / `f57` | 成交量 / 成交额 |
| `f58` / `f59` | 振幅 / 涨跌幅 |
| `f60` / `f61` | 涨跌额 / 换手率 |

ShadowFlow 的个股研究归档固定使用 `klt=5&fqt=0`，并要求单股当日完整返回 48 根后才写入。日 K 前复权早期价格可能为负数，不能仅因负值判定响应无效。

2026-08-16 的基线样例：`90.BK1650` 返回 105 根；`90.BK0490` 返回 460 根且 `dktotal=6448`；`1.600519` 返回 460 根且 `dktotal=5983`。这些数量只用于回归排查，不应写成业务断言。

2026-08-17 使用完整反爬特征重新验证：

| 标的 | 类型 | 有效响应 | 返回摘要 |
|---|---|---|---|
| `90.BK1650` | 概念“通信技术” | HTTP 200、`rc=0` | 105 根，`2026-03-16` 至 `2026-08-14` |
| `90.BK0448` | 行业“通信设备” | HTTP 200、`rc=0` | 460 根，`dktotal=6448`，最新日期 `2026-08-14` |

两个响应都校验了代码、名称、K 线数组和日期，不是错误页或空数据。这组结果证明板块历史日 K 的接口能力与参数有效，但不证明同一配置可以连续批量抓取。冷却后对 `BK0448` 发起 `beg=20260812&end=20260814` 的精确三日请求仍被服务端无响应断开，因此该次实验没有取得精确三日响应，不能把它记录为成功样例。

### 4.1 真实页面的预取行为

2026-08-17 使用同一真实浏览器会话加载 `BK0448` 页面，页面资源清单记录到 30 个历史 K 请求，缓存破坏参数 `_` 的最小值与最大值仅相差 142 毫秒：

| `klt` | 周期 | 请求数 | 观察到的 `lmt` |
|---|---|---:|---|
| `101` | 日 K | 13 | `1000000`、`120`、`1` |
| `102` | 周 K | 7 | `1000000`、`120`、`1` |
| `103` | 月 K | 10 | `1000000`、`120`、`1`、`287` |

这批请求使用 11 个 JSONP 回调名。页面随后成功绘制日 K、周 K 和月 K。由此可确认：

- 真实页面会在初始化阶段集中预取多个 K 线周期，不遵守“每个请求间隔若干秒”的串行模型。
- 点击“日 K/周 K/月 K”不能直接用来测接口请求间隔，因为相应数据可能已经预取。
- 按钮高亮早于图表更新，旧请求的延迟响应还可能覆盖较新的 UI 状态；必须结合资源时间线和最终图形判断。
- 页面延迟显示日 K 不等于服务端存在冷却时间，可能只是预取、回调和图表渲染的异步过程。

### 4.2 Cookie 复用与同期浏览器对照

2026-08-17 的纯 HTTP 与浏览器对照结果：

| 实验 | 结果 |
|---|---|
| 生成 Cookie 首次请求 | 成功 |
| 同一冻结 Cookie，约 3 秒内再请求 5 次 | 5 次全部成功 |
| 同一冻结 Cookie，10 秒后请求 | 空响应 |
| 固定身份字段、刷新 `st_psi`，10/20 秒请求 | 均为空响应 |
| curl 完全不带 Cookie | 单次成功 |
| 成功浏览器 HAR | 请求无 Cookie，响应无 `Set-Cookie` |
| 固定到曾成功的两个边缘 IP | 当次均为空响应 |
| curl 同期空响应时刷新真实页面 | 浏览器成功取得 `BK1650` 日 K |

因此不能为 Cookie 定义一个确定的有效期，也不能把 10 秒后的失败称为 CD。纯 HTTP 的短时成功窗口确实存在过，但浏览器在同一外部环境中仍可正常工作，表明问题更接近客户端分类或连接行为差异。

### 4.3 固定出口与固定边缘状态窗口

2026-08-17 快速实验全程使用同一公网出口 IPv4，出口仅以哈希核对且实验前后未变化。curl 使用：

```text
--noproxy '*'
-4
--http1.1
--resolve push2his.eastmoney.com:443:<固定边缘 IP>
```

第一组使用当时 DNS 返回的边缘 `117.184.38.143`：

| 时间线 | 结果 |
|---|---|
| 静默 120 秒后，无 Cookie | 空响应 |
| 紧接着生成新 Cookie | 空响应 |
| 再静默约 60 秒，无 Cookie | 成功 |
| 成功后约 200 毫秒生成新 Cookie | 空响应 |

这说明“生成 Cookie”本身不能打开一个处于拒绝状态的客户端；静默恢复也可能发生在完全无 Cookie 的请求上。

第二组固定到此前成功过的边缘 `101.42.128.173`：

| 实验 | 结果 |
|---|---|
| 静默 60 秒后，无 Cookie 请求 `BK1650` | 空响应 |
| 随后新 Cookie 请求 `BK1650` | 成功 |
| 约 500 毫秒后，无 Cookie 请求 `BK1650` | 成功 |
| 再约 500 毫秒，无 Cookie 请求 `BK0448` | 空响应 |
| 独立静默 60 秒后，新 Cookie 建立 | 成功 |
| 同 Cookie 间隔 1/2/5 秒 | 均成功 |
| 同 Cookie 间隔 8 秒 | 空响应 |
| 失效后新 Cookie：0/2/5/10/20 秒 | 均为空响应 |
| 失效后新 Cookie：40 秒 | 成功 |
| 恢复 Cookie 静默 10 秒后复用 | 空响应 |
| curl 空响应后的同期真实浏览器 | `BK1650` 日 K 成功 |

本次快速实验得到的是当前 curl 模式下的操作窗口：

- 同标的无 Cookie 可以短时继承成功状态，跨标的继承未成立。
- 活跃复用最大成功间隔为 5 秒，最小失败间隔为 8 秒。
- 连续恢复探针下，20 秒不足，40 秒成功。
- 这些数值不能推广为东方财富公开规则，也不能替代后续多轮独立重复。

## 5. 分时降级接口

```text

```

ShadowFlow 在五分钟 K 失败时使用 `trends2` 的 241 根当日一分钟数据聚合成 48 根五分钟 K。核心参数为：

secid=<market.code>
ndays=5
iscr=0
ut=fa5fd1943c7b386f172d6893dbfba10b
fields1=f1,f2,f3,f4,f5,f6,f7,f8,f9,f10,f11,f12,f13
fields2=f51,f52,f53,f54,f55,f56,f57,f58,f59,f60,f61,f62

聚合和完整性口径见 [项目记忆“盘后长期归档口径”](../项目记忆.md#十三盘后长期归档口径2026-08-16)。主域空响应、网络错误或明确临时服务错误时可以切换候选域；业务参数错误、数据日期错误和结构错误不能靠盲目切域掩盖。

## 6. 同域相关接口

以下接口可能受同一类客户端特征校验影响。Cookie 是否参与判定、哪些连接或请求特征有效，均未逐端点完成最小化验证：

| 用途 | 路径 |
|---|---|
| 单标的行情 | `/api/qt/stock/get` |
| 板块或成分股列表 | `/api/qt/clist/get` |
| 个股关联板块 | `/api/qt/slist/get` |
| 分时 | `/api/qt/stock/trends2/get` |
| 资金流 K 线 | `/api/qt/stock/fflow/kline/get` |
| 批量行情 | `/api/qt/ulist/get` |

新端点接入时应先沿用完整特征，再通过至少 5 次重复测试做删减，不要把单次成功视为稳定合约。

## 7. 重试、限速与熔断

1. 当前没有证据支持 `push2his` 存在统一的安全 QPS 或 10/20 秒固定冷却时间。限速仍可作为降低运行风险的工程措施，但不能写成已验证的反爬规则。
2. 若使用 Cookie，应在逻辑会话内复用身份字段，不要每个请求都创建新身份；但无 Cookie 浏览器和 curl 也都出现过成功，不能把 Cookie 当作必选认证步骤。
3. 脚本客户端第一次出现 `Empty reply`、`EOF` 或连接重置时，停止当前批次并保存会话，不要立即通过换 Cookie、切换 IP 协议或不断延长等待时间猜测冷却值。
4. 恢复实验必须区分“原成功 Cookie 复用”“每次新 Cookie”“无 Cookie curl”和“真实浏览器”。不同客户端模型的结果不能混合推导。
5. 若需要设置重试等待，数值只能作为当前客户端的临时退避策略；应通过该客户端自身的重复实验校准，不得宣称为东方财富接口的全局 CD。
6. 日线数据仍应每日缓存；生产批量任务应限制并发、设置熔断并记录端点、`secid`、会话标识、HTTP 阶段和响应长度。日志中不要打印完整 Cookie。

对本次验证使用的 curl 模式，可以采用以下临时实验策略：

- 成功后按同一 `secid` 组成短批次，请求间隔不超过 5 秒。
- 不依赖“去掉 Cookie 后整个出口 IP 都已放行”；同标的继承成功不代表其他板块可用。
- 第一次空响应立即结束当前短批次，不在 0 至 20 秒内循环换 Cookie。
- 至少退避 40 秒后建立新 Cookie，并重新做单请求成功校验。
- 该策略只用于后续验证，不直接替换 ShadowFlow 的生产采集策略。

同一成功 Cookie 的短时复用已经验证，但稳定性仍未建立。尚未完成的是标准 HTTP 客户端与真实浏览器在相同 TLS、连接复用、请求头顺序和请求序列下的差异定位。在完成前，不应把 `push2his` 用作数百个板块的生产历史回填源。

当前代码与本规范仍有差距：`backend/internal/datasource/eastmoney/stock_kline.go` 使用简化请求头、未稳定复刻真实浏览器的连接与请求行为，也未记录足够的连接和响应阶段信息。现有 `trends2` 降级和连续失败熔断可以保留，但后续修复 K 线主接口时应以本文为实现依据。

## 8. 故障判定与排查

| 表现 | 优先检查 |
|---|---|
| 无 HTTP 响应、`EOF`、连接重置 | 当前 curl 状态窗口、客户端连接特征和请求行为；Cookie 不是唯一变量 |
| 403 或验证码页 | JS 挑战或更强风控，重新抓取浏览器流程 |
| 200 但 `data` 为空 | `secid`、日期、周期、字段参数、交易状态或风控降级 |
| JSONP 解析失败 | `cb` 去壳、压缩解码、响应截断或返回了错误页 |
| 时好时坏且实验结论冲突 | 降低频率、等待惩罚衰减，再用隔离会话重复至少 5 次 |

排查顺序：

1. 记录绝对时间、出口 IP 哈希、东财边缘 IP、`secid`、Cookie 会话哈希、HTTP 阶段和响应长度，不记录完整 Cookie。
2. 固定出口协议和边缘 IP，先用相同 `secid` 重现，不能把同标的继承推广为跨板块的全 IP 放行。
3. curl 首次空响应后立即结束当前短批次，不在 0 至 20 秒内循环换 Cookie；当前验证使用的 curl 模式至少退避 40 秒再建会话。
4. curl 失败时同步用真实浏览器加载相同标的。浏览器成功而 curl 失败时，优先比较 TLS/HTTP 栈、请求头顺序、连接复用和请求序列。
5. 每个关键结论至少独立重复 5 次。单次成功、单次失败或一次等待恢复只能作为样例，不能写成东方财富公开规则。
