## 配置与读写边界

`SHADOWFLOW_COLD_DATABASE_PATH` 为空时保持单库行为。启用时必须指向已有冷库；缺失、不可读或列结构不兼容均导致启动失败，不会创建一个空文件掩盖数据缺失。生产容器路径示例为 `/data/shadowflow-cold.db`。

后端只读冷库。维护工具负责冷库写入；热冷重复的分钟行按原主键合并，热库中的修正优先。开启冷库后，后端旧的 `CleanupArchivedIntraday` 不再直接删除分钟数据，研究原始响应也不再被通用短期清理删除。

五分钟资金、个股 K 线、特征和正式日档仍在主库，原研究导出接口继续读取这些未搬迁的数据。单分钟提取与离线救援需显式提供 `--cold-database`；缺少采集运行凭据时仍拒绝宣称来源完整，不虚构 provenance。

## 冷库升级

使用当前主库真实 `sqlite_schema` 定义建立新冷库，不能再次用 CTAS 作为正式表结构。原表的列、主键、NOT NULL/CHECK 约束及必要查询索引得到保留。所有旧分钟/原始响应逐表按原主键排序，核对行数和全字段摘要，执行新库 `PRAGMA integrity_check`，再原子发布；旧文件保留为 `.pre-upgrade-*`。

运行示例（20:00–06:00 北京时间）：

```sh
SQLITE_TMPDIR=/mnt/data/shadowflow/data python3 scripts/archive_intraday.py upgrade \
  --database /mnt/data/shadowflow/data/shadowflow.db \
  --cold-database /mnt/data/shadowflow/data/shadowflow-cold.db --apply
```

升级完成后，确认 uid/gid 10001 可以读写正式冷库和目录。旧冷库之前属于 root；root 执行升级时正式冷库及共享维护锁跟随主库所有者，旧文件保持不动。仍需实际检查维护写权限，不能错误地认为只读 API 的权限测试证明维护写权限也正确。

## 归档流程

维护程序与双库快照程序对主库旁的 `.archive.lock` 使用内核 `flock`。锁文件本身可长期存在；是否占用应检查真实句柄/锁或进程，不通过删除锁文件“修复”。默认单次最多处理一个日期，允许显式提升到 31 个日期。

每个日期的处理顺序：

1. 主库短期写事务固定该日来源，冷库事务复制分钟与原始响应，保存尚存的采集运行记录。
2. 按原主键核对所有复制行的完整内容摘要，而不只比较行数。
3. 冷库以 DELETE journal、FULL synchronous 持久提交并记录 `copied`。
4. 再删除已验证的主库来源并提交，记录 `pruned`。

复制提交后崩溃只会留下重复副本；API 合并去重，下一次执行可重试。后来补入的旧日修正会更新对应冷库行，不删除冷库的其他分钟。没有跨 WAL 附加库“原子搬迁”的假设。

归档可预览：

```sh
python3 scripts/archive_intraday.py archive \
  --database /mnt/data/shadowflow/data/shadowflow.db \
  --cold-database /mnt/data/shadowflow/data/shadowflow-cold.db \
  --calendar backend/config/trading_calendar.json --keep-trading-days 10
```

盘后入口为容器内 `/app/scripts/auto-archive.sh`，它使用与 API 相同的冷库环境变量。只有线上读路由、备份和恢复验收通过后才安装宿主机 cron。建议 21:40 串行执行，不覆盖现有备份任务；首次执行核查日志和实际退出码。没有每天 VACUUM；空闲页由 SQLite 重用，压实仅作为非采集时段的人工维护。

## 备份与恢复

开启冷库时原 `backup.sh` 自动生成 `.bundle.tar`，内含两个 gzip 数据库、已保存的历年日历（若存在）及版本化 `manifest.json`，外部 `.sha256` 是发布完成标记。每个数据库快照都通过完整性检查，清单记录未压缩大小和摘要；验证拒绝额外路径、重复 tar 成员、链接、无效摘要和缺失配对库。

搬迁互斥只覆盖两个在线快照阶段；之后校验、压缩处理固定副本，不长期锁住线上读事务。保留策略在冷库模式下同时计数有效旧单库备份和新双库包，不清理手工、损坏或半成品归档。停止冷库模式后旧单库脚本不会自动清理双库包，避免误删历史配对备份。

```sh
docker exec shadowflow /app/scripts/backup.sh
docker exec shadowflow /app/scripts/restore.sh /backups/shadowflow-TIMESTAMP.bundle.tar --dry-run
```

恢复演练必须使用临时目录或隔离容器，不替换线上库。真正恢复前先停止服务。启用冷库时拒绝只恢复旧 `.db.gz`，避免配对库来自不同状态。

正式恢复使用跨容器共享的 `.service.lock` 排除仍在用库的服务和采集进程，不只依赖容器内 `pgrep`。取得独占锁后先保存已有两库的在线安全副本，再持久写入 `<main>.restore-in-progress` 标记，随后发布两库。两次文件替换并非崩溃原子操作；标记未移除时后端拒绝启动。中断后重试完整恢复或使用保留的安全副本，不手工删除标记强行开服务。
