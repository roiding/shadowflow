## 已确认的历史读取问题

同一日期、板块及分钟，在 API 与冷库的结果不同：

| 查询 | 结果 |
| --- | --- |
| API：行业 BK0448，2026-10-09 的 intraday | HTTP 200，0 行 |
| 冷库：同日期、同板块 | 240 行，09:31 至 15:00 |
| API：行业 2026-10-09 09:36 的 ranks | HTTP 200，0 行 |
| 冷库：同日期、同类型、同分钟 | 71 行 |

原因可在 `backend/internal/repository/sqlite/query.go` 中确认：`IntradaySeries` 和 `RankAt` 只查询主库，之后尝试主库的五分钟/盘后归档，没有冷库读取入口。并非所有历史接口都空；保留在主库的五分钟归档仍可能可读，但已搬走的一分钟详情没有被透明保留。

冷库为 root 所有、0644 权限。本次使用容器 uid/gid `10001:10001` 检查 `/data/shadowflow-cold.db`，确认可读。因此当前空结果不是文件读取权限拒绝。

## 实际 API 延迟

测量方式：生产主机回环地址，串行请求，每个接口两次；无并发压力测试，没有请求会调用上游行情的 board-quotes 接口。样本数不足以计算可靠 P95，包含缓存及运行时影响，不代表用户浏览器的总加载时间。

| 请求 | 第一次 | 第二次 | 返回数据 |
| --- | ---: | ---: | --- |
| 最新行业榜单 | 1,372.62 ms | 1,444.42 ms | 71 行 |
| 最新概念榜单 | 2,402.40 ms | 2,357.57 ms | 342 行 |
| 当日 BK0448 分钟曲线 | 39.10 ms | 40.30 ms | 上午 120 点 |
| 000001，10 月 23 日五分钟 | 21.68 ms | 14.57 ms | 48 点，资金/K 线均可用 |
| 10 月 23 日个股日档第一页 | 61.56 ms | 51.75 ms | 50 行，总数 5,377 |
| BK0448，09-21 至 10-23 五分钟趋势 | 332.85 ms | 149.72 ms | 672 点，不代表覆盖区间每一天完整 |

最新榜单中的工作数据查找为：

```sql
SELECT max(snapshot_at)
FROM rank_intraday_work
WHERE rank_type = ?;
```

现有 `idx_intraday_latest` 以 `trade_date` 为首列，执行计划对该查询没有按 `rank_type` 定位的搜索条件。使用主机 Python SQLite 驱动，单独的上述查找行业耗时 518.76 ms、概念耗时 770.00 ms；取得已知时间的代码/排名行只耗时 10.99 ms 和 4.27 ms。它是已确认的显著慢点，但这些驱动层时间不能当作 Go API 的精确耗时拆分。

建议下一步验证按 `(rank_type, snapshot_at DESC, rank)` 排列的最新工作快照索引，同时保留“旧工作数据不能遮住较新盘后归档、同时间优先盘后档”的现有语义。在代表性数据上比较实际执行计划与 API 延迟后再部署，不能仅凭索引名称或主库体积宣称解决。

个股点查实测使用此前新增的 `idx_stock_research_code_date`，当前精确日期查询没有临时排序。源代码还已有 `(trade_date, code, minute_index)` 索引。因此此前用 `trade_date >= ? ORDER BY minute_index` 的示例来判断个股页面慢、排序仍在，并不等同于真正的页面查询；现阶段不应继续为这个快接口盲目增加索引。

## 尚未完成的热冷设计

- 读取：为 `IntradaySeries`、`RankAt` 及需要原始工作数据的恢复/导出入口补齐冷库读路由，避免把“有冷数据但尚未接入”表现为真正没有数据。
- 备份：`scripts/backup.sh` 及容器中已安装的脚本仅对 `SHADOWFLOW_DATABASE_PATH` 做 `.backup`，没有冷库备份。需设计包含两库的校验清单、恢复流程和保留策略。
- 模式：当前冷表由 CTAS 生成，没有原表的主键、NOT NULL/CHECK 约束、索引和模式版本。先验证现有数据，再迁移到保留约束的正式结构。
- 边界：2026-10-12 是固定日期，不是已实现的“滚动十个交易日”策略。滚动窗口应使用交易日历，不能以十个自然日替代。
- 安全：WAL 主库与附加冷库的复制/删除事务不能假定跨文件崩溃原子性。正式归档需先复制、验证及记录状态，读取可用后再决定何时删除热副本；保留可回滚备份。
- 范围：此次搬走的是旧分钟工作表，个股五分钟大表等仍在主库。是否进一步做按月分区/归档属于下一阶段设计，不应直接继续大规模搬迁。

建议顺序：先恢复历史读可见性并补齐冷库备份，再部署经过基准验证的榜单索引，最后制定正式滚动归档。未经完整验证，不清理现有备份、冷库或救援快照。
